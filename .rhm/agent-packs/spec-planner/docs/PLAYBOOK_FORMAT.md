# PLAYBOOK.md — HM Harness direct artifact

`final/PLAYBOOK.md` is **not** generated by a Python template and is **not**
imported from Cursor Plan Mode on this harness.

On **HM Harness (Omnigent / Claude Code)** you **Write** `final/PLAYBOOK.md`
directly under `workspace/<task-id>/` with the same letter-to-letter depth Cursor
Plan Mode would produce. **Do not** call `SwitchMode`, Plan Mode, or
`playbook-importer` — those tools do not exist here.

Cursor Cloud’s twin pack still uses SwitchMode → Plan → playbook-importer.
This HM pack’s exit is: write `final/` files → run validators → emit RHM wire JSON.

## Constructive improvement (do not remove depth)

| Keep (as before) | Improve |
|------------------|---------|
| Every implementation **STEP** from `planning/implementation-plan.yaml` | Shape as plan **todos** + markdown body |
| Letter-to-letter pins (files, exact snippets, commands, verify) | Embed them in plan prose |
| Decisions, constraints, coverage / residual scope | Situation-shaped H2s (only sections this job needs) |
| iDAG linkage (`playbook_ref` / STEP ids) | Todos and body still name STEP ids |

**Forbidden:** thinning STEPs, dropping todos that map to STEPs, or “format cleanup”
that leaves the coding agent to invent.

**Forbidden on HM:** emitting `quality_gate: FAIL` / blocked stubs because SwitchMode
is unavailable. Keep using Write/Edit until real `final/` artifacts exist with
`quality_gate: PASS` (or a true Spec-level block after real research — never an
“environment ended” stub).

Machine STEPs remain SoT in `planning/implementation-plan.yaml`. PLAYBOOK must still
be rich enough that a coding agent can execute **without rediscovering** those STEPs.

## Mandatory generation flow (HM Harness)

```
Agent turn (research → decisions → STEPs / iDAG / critic …)
        │
        ▼
Write workspace/<task-id>/planning/*.yaml  (STEPs + iDAG)
        │
        ▼
Write workspace/<task-id>/final/PLAYBOOK.md
        │   YAML frontmatter: name, overview, todos (≈ STEPs)
        │   body: letter-to-letter depth + pins (see placeholder below)
        ▼
Write final/HANDOFF.md, final/DAG.yaml, final/PACKAGE_MANIFEST.yaml
        │
        ▼
Run scripts/validate-playbook.py --workspace workspace/<task-id>
        │   (+ validate-dag / check-handoff when present)
        ▼
Emit one ```json``` spec_planner_package (quality_gate PASS) for RHM
```

### Rules

1. **Never** SwitchMode / Cursor Plan Mode / playbook-importer on this harness.
2. **Write** `final/PLAYBOOK.md` yourself with Cursor-plan-shaped frontmatter + body.
3. YAML STEPs + iDAG stay in `planning/`; PLAYBOOK carries the same work for the coding agent.
4. Optional receipt: write `final/PLAYBOOK.hm.json` with `{"authored":"hm_harness","path":"final/PLAYBOOK.md"}` — **not** required.
5. Do **not** invent thin STEPs; do **not** stop at Ready; do **not** emit FAIL stubs.
6. **Never** write `cursor/hmh-*` or `rhm/pack/*` into PLAYBOOK/HANDOFF as the required
   push/delivery branch — those are this planner agent's ephemeral checkout names, not
   Spec delivery. Use Spec-named branch, `main`, or “implementer branch from main”.

## What “good” looks like

- YAML frontmatter: `name`, `overview`, `todos` (`id`, `content`, `status`), `isProject`
- Todos cover the same work as STEPs (STEP ids visible in todo content or body)
- Body: situation-shaped H2s **as needed** — Decisions / Constraint / Concrete change / Files / Verify / Out of scope, etc.
- Letter-to-letter pins still present in the plan body where the job needs them
- **No thinner** than the prior STEP package for the same Spec
- Source / command pins in the body use the **placeholder below** — never a loose dump

## How pins appear in PLAYBOOK.md / HANDOFF.md

Use labeled fences — never a bare dump:

~~~markdown
exact_snippet: path/to/file.ext
~~~lang
…pinned source…
~~~

~~~markdown
exact_commands:
~~~bash
…commands…
